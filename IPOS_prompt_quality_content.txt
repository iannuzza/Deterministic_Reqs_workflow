- `reset`
- `signal`
- `memory`

- `dsp` as a substring inside `ADSP`

### Mandatory corrections
1. **ADSP**

   - Require a real standalone DSP/control-signal condition.

2. **Regmap**

   - Do not assign “power, clock, and reset sequencing” from mere reset mentions in register/configuration context.
   - Power/clock/reset summaries require truly power/clock/reset functional evidence.

3. **Main Controller**
   - Do not classify requirement-level evidence into power/clock/reset sequencing from isolated `reset`.
   - Reject evidence like ADC-error-cap reset behavior unless it contains a valid supported functional combination for that topic.

4. **Smart FIFO**

     - `The parameter ...`
     - equivalent article/value/address-definition forms
   - Do not promote such fragments into functional topics.

## Track 4: descriptive quality and abstraction
Apply these rules to all IPOS descriptive sections, especially:
- `Functionality`
- `Supported functions and scope`
- `Internal structure`
- `Internal blocks or functions`
- `General architecture`

### Required behavior
- Write **high-level block-local engineering summaries**
- Focus on:
  - main purpose
  - local scope
  - supported local capabilities
  - real local internal structure/functions only if evidenced
- Keep implementation/normative detail in requirement sections only

### Mandatory output rules
1. **Functionality**
   - Open from the block’s main local purpose in substance like:
     - “The main purpose of this block is ...”
   - No bare-verb openings or low-level fragments when a meaningful high-level purpose can be formed.

2. **Supported functions and scope**
   - Describe **what the block locally enables**, not requirement details.
   - Do **not** dump:
     - exact clock-ratio constraints
     - exact address ranges
     - exact register names/addresses
     - preload trigger details
     - protocol-mode lists copied from requirements
   - Example: for **I2C-SPI-AHB**, summarize as local protocol bridging / transaction translation / local read-write handling / local buffering support if supported, but do **not** emit the detailed requirement body here.

3. **Internal structure**
   - Do not emit this section from:
     - port counts
     - interface counts
     - endpoint counts
     - boundary counts
     - generic structural filler
   - Emit only if there is real evidence of internal composition/organization.

4. **Internal blocks or functions**
   - Emit only when explicit local internal functions are evidenced.
   - Do not promote parameter statements, register-field fragments, low-level values, or topic leftovers.

5. **General architecture**
   - Do not emit isolated low-level fragments such as:
     - `rd_to_max_val`
     - `ip_version`
     - timer values
     - register field/value snippets
     - OCR residue
     - broken phrases
   - If no coherent local architectural summary exists, omit the section.

6. **Block-local scope**
   - Do not import DRS/system themes such as:
     - power and clock islands
     - arbitration and control
     - shared digital resources
   - unless clearly supported as real local block functionality.

7. **Omit unsupported content**
   - If the evidence cannot support a clean, deterministic, high-level, block-local synthesis, omit the paragraph.
