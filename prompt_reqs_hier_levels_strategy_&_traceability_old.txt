## Target strategy

### A. Hierarchical requirement-generation strategy
Use this hierarchy/ownership model:

- **SRS** contains only system-level requirements and descriptions:
  - system behavior
  - externally visible behavior
  - system modes/power states
  - system-level performance/safety/monitoring
  - top-level external interfaces
  - cross-domain system coordination
  - system-level power-domain architecture, low-power strategy, on/off sequencing, wake-up features

- **DRS** contains only top-digital / architecture / integration-level requirements and descriptions:
  - digital inter-block coordination
  - shared digital resources
  - digital clock/reset/power coordination
  - firmware-visible top-digital behavior
  - digital decomposition of system modes / low-power / wake-up
  - top-level digital interface contracts

- **ARS** contains only top-analog / mixed-signal / architecture-level requirements and descriptions:
  - analog partitioning and coordination
  - analog supply/bias/power-domain behavior
  - analog sequencing / wake-up / settling / retention / isolation at architecture level
  - analog/digital interaction constraints

- **IPOS** contains the full detailed block-local requirements and descriptions of one block:
  - local functional behavior
  - local sequencing / state-machine behavior
  - local register / interface / timing / control / error details
  - local low-power / reset / init behavior
  - specific block IO list
  - specific block port map

Rules:
- detailed block-local requirements belong primarily in IPOS
- block-specific IO lists and port maps belong only in IPOS
- higher-level specs may contain the same topic only at their own abstraction level
- do not duplicate the same detailed block-local requirement text across SRS / DRS / ARS / IPOS

### B. Source and supplementary-source strategy
- primary top/source specs may contain:
  - system-level requirements
  - architecture-level requirements
  - block-local requirements
- supplementary source specs may also be:
  - domain-level
  - architecture-level
  - block-dedicated
  - already IPOS-like

Rules:
- if a supplementary source is dedicated to one block, it shall primarily feed that block’s IPOS
- only the subset with true higher-level architecture/integration relevance shall also appear in DRS or ARS
- if a top/source spec already contains clearly block-local requirements, those may also feed the corresponding IPOS directly
- do not invent artificial intermediate DRS/ARS parents when no meaningful intermediate generated parent exists

### C. Traceability strategy
Use this rule:
- each generated requirement shall normally render `Covers:` only to the **nearest relevant approved parent** in the decomposition path
- full end-to-end lineage must still be preserved in the authoritative traceability model and reports
- direct source-to-IPOS or supplementary-source-to-IPOS traceability is allowed whenever the requirement is already clearly block-local and no meaningful intermediate generated parent exists

Normal rendered Covers path:
- SRS -> Source
- DRS -> SRS
- ARS -> SRS
- Digital IPOS -> DRS
- Analog IPOS -> ARS

Allowed direct block-local path:
- top/source block-local requirement -> owning IPOS
- supplementary block-local requirement -> owning IPOS

### D. Traceability accounting strategy
Do not use a naive rule that every source requirement must appear in every level.

Instead:
- define traceability/coverage by requirement class and ownership
- count a requirement as fully covered when it reaches all required downstream targets for its approved class
- distinguish:
  - covered
  - under-covered
  - over-propagated
  - misallocated
  - orphaned
- report both normal hierarchical paths and direct block-local source-to-IPOS paths

### E. Valid downstream coverage targets per class

- system_level
- top_digital_architecture
- top_analog_architecture
- shared_cross_domain
- block_local_digital
- block_local_analog
- interface_contract
- supplementary_block_local
- descriptive_only / non-propagating if applicable

For each approved class, define:
- valid downstream target specs
- required downstream target specs
- allowed direct-source-to-IPOS behavior
- whether DRS/ARS intermediate coverage is required, optional, or not applicable

### F. Coherence and full downward coverage
Guarantee coherence and full requirement coverage downward from both:
- primary source top specs
- supplementary source specs

This means:
- every approved in-scope source/supplementary-source requirement must have a valid coverage classification
- every requirement must reach all required downstream targets according to that classification
- direct source-to-IPOS paths must be treated as valid when justified, not as missing coverage
- higher-level omission must be distinguishable from valid block-local direct allocation
- reports and validators must detect:
  - missing required coverage
  - wrong owner/block/domain allocation
  - wrong hierarchy placement
  - unjustified duplication
  - unjustified skipped hierarchy
